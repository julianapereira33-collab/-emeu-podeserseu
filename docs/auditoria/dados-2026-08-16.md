## Limitação importante (leia antes de tudo)

O briefing dizia que o snapshot tinha **"todas as ~20 funções SECURITY DEFINER com corpo completo"**.
Ele **não tem**. O snapshot traz um *resumo em prosa* de cada função (o que ela faz), não o `prosrc`/
`pg_get_functiondef`. Sem o corpo, **é impossível afirmar** se uma função usa `<>` ou `IS DISTINCT FROM`.

Isso muda a natureza do item 1 do escopo: em vez de "aqui estão os trechos exatos com o bug", entrego
**hipóteses ranqueadas por risco, com o trecho de código que espero encontrar em cada uma e o motivo
técnico exato** — mais a query que resolve tudo de uma vez (Q1/Q2 na última seção). Prefiro isso a
inventar trechos que eu não li, o que seria pior que não responder.

Um segundo sinal de que o snapshot está incompleto: o README descreve uma lógica de anti-fraude de
cashback (5 cliques → R$15, throttle de IP em 24h, teto de 3 créditos/dia) que **não existe em lugar

sobre `cliques_compartilhamento` que **não aparece na lista de funções do snapshot**. Ou seja: existe
pelo menos uma função `SECURITY DEFINER` em produção que ninguém auditou hoje.

## 1. Caça ao padrão de bug (`<>` vs `IS DISTINCT FROM`)

### Relembrando o padrão, pra referência

`current_usuario_id()` devolve `NULL` quando não há sessão. Em SQL, `qualquer_coisa <> NULL` não é
`true` nem `false` — é `NULL`. E `IF NULL THEN ... END IF` **não executa o bloco**. Resultado: a linha
que deveria dizer "você não é o dono, sai daqui" simplesmente não roda. `IS DISTINCT FROM` é a versão
que trata NULL como um valor comum e devolve `true`/`false` de verdade.

O mesmo raciocínio vale para **qualquer** valor que possa ser NULL dos dois lados da comparação — não
só `current_usuario_id()`. É por isso que a caça abaixo vai além do que já foi corrigido.

### A1 — `fn_bloqueia_campos_privilegiados_usuarios()` — **P0, maior risco do sistema hoje**

Essa é a função que impede uma usuária comum de mudar o próprio `papel`, `banido_em`, `recrutado_por`
e `auth_user_id`. Ela é a **única** defesa nesses campos: a RLS `usuarios_update_own_or_admin`
**permite** que qualquer pessoa dê UPDATE na própria linha de `usuarios`. Sem o trigger funcionando,
qualquer usuária autenticada consegue mandar um PATCH direto na API REST do Supabase (não precisa nem
passar pelo site) alterando esses campos.

Três das quatro colunas protegidas **são nulas** segundo o próprio snapshot:
`recrutado_por uuid?`, `banido_em timestamptz?`, `auth_user_id uuid?`.

Se o corpo for o formato mais natural de escrever isso —

```sql
if not is_admin() and (
     new.papel         <> old.papel
  or new.recrutado_por <> old.recrutado_por
  or new.banido_em     <> old.banido_em
  or new.auth_user_id  <> old.auth_user_id
) then
  raise exception 'campo privilegiado';
end if;
```

— então cada operando com NULL vira `NULL`, e `false OR NULL` = `NULL` → **o `raise` não acontece**.
Dois ataques concretos, cada um de uma linha:

| Ataque | Como | Impacto |
|---|---|---|
| **Auto-desbanimento** | vendedora banida faz `PATCH usuarios?id=eq.<ela> {"banido_em": null}`. `NULL <> '2026-08-10'` = NULL → passa | O sistema de exclusividade/banimento (2 denúncias = banimento) deixa de valer. É a única punição que existe hoje |
| **Auto-vínculo a embaixadora** | loja faz `PATCH usuarios?id=eq.<ela> {"recrutado_por": "<uuid da cúmplice>"}`. `<uuid> <> NULL` = NULL → passa | Toda venda dela passa a gerar **override de 5%** para uma conta amiga. Dinheiro real saindo do caixa, com aparência de comissão legítima |

Repare que o ataque exige alterar **só o campo nulo, isolado** — se a pessoa mandar `papel` junto
(campo não-nulo), a expressão vira `true OR NULL` = `true` e o bloqueio funciona. Isso explica por que
o bug pode existir há meses sem ninguém notar: no uso normal (admin promovendo alguém pelo painel) ele
nunca aparece.

**Ponto de atenção extra:** se `papel` também aceitar NULL, existe uma escalada em dois passos —
primeiro `{"papel": null}` (passa, porque `NULL <> '{vendedora}'` = NULL), depois `{"papel":
["admin"]}` (passa também, porque agora o `old` é NULL). Isso daria **acesso de admin** a qualquer
usuária. O snapshot sugere que `papel` é `NOT NULL DEFAULT '{}'`, mas isso precisa ser confirmado
(Q7 traz o `is_nullable` de todas as colunas).

**Correção esperada** (aplicar só depois de confirmar o corpo): trocar as 4 comparações por
`IS DISTINCT FROM` e, de quebra, colocar `NOT NULL` em `papel`.

### A2 — `confirmar_pagamento_taxa` e `confirmar_pagamento_atendimento` — **P0**

A minha memória do incidente registra que o fix de **13/08 nessas duas funções foi de *grant*, não de
código**: "corrigido movendo a chamada pro cliente de service role no Next.js e revogando `EXECUTE` de
`authenticated`". O fix de 16/08 (que trocou `<>` por `IS DISTINCT FROM`) atingiu apenas
`iniciar_pagamento_pix`, `iniciar_pagamento_pix_atendimento` e `registrar_intencao_pagamento_taxa`.

Conclusão: **é bem provável que o `<>` ainda esteja vivo no corpo dessas duas funções**, e que a única
coisa impedindo o bypass hoje seja o GRANT. Isso é frágil por um motivo já comprovado neste projeto:
**um `CREATE OR REPLACE FUNCTION` reseta os grants pra `PUBLIC`**. Ou seja, a próxima vez que alguém
(ou um agente) mexer nessas funções sem lembrar do `revoke ... from public`, o bypass volta —
e o que está do outro lado dele é *confirmar que uma taxa foi paga sem pagar*: contato liberado,
cashback creditado, comissões geradas.

Além disso, essas duas funções têm um segundo ponto do mesmo padrão, que **ninguém olhou ainda**:

```sql
if auth.role() <> 'service_role' and v_dono <> current_usuario_id() then
     ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ aqui também
```

`auth.role()` devolve `NULL` quando não há claim de role no JWT. `NULL <> 'service_role'` = `NULL`, e
`NULL AND qualquer_coisa` nunca é `true` → **a checagem inteira é pulada**. Ou seja, mesmo que a
comparação de dono fosse corrigida, um chamador sem role no token passaria batido. A forma correta é
`coalesce(auth.role(), '') <> 'service_role'` ou `auth.role() IS DISTINCT FROM 'service_role'`.

**Recomendação:** corrigir o corpo das duas (defesa em profundidade), mantendo o revoke. Não confiar
em uma única camada quando a camada única já provou ser volátil.

### A3 — varredura de GRANT: `proacl IS NULL` = `PUBLIC` pode executar — **P0**

Detalhe do Postgres que casa exatamente com a pegadinha já confirmada: quando `pg_proc.proacl` está
**NULL**, isso não significa "ninguém tem permissão" — significa "permissões padrão", e o padrão para
funções é **`EXECUTE` para `PUBLIC`**. Como `anon` e `authenticated` pertencem a `PUBLIC`, qualquer
função nessa situação é chamável por um visitante sem login.

O snapshot afirma que `handle_new_auth_user`, `expirar_reservas_vencidas`, `fn_*` e `trg_*` estão com
"ninguém direto". Isso precisa ser verificado com `proacl`, não por dedução (Q6). Duas em especial:

- **`fn_enviar_whatsapp_evolution(whatsapp, mensagem)`** — se estiver exposta, qualquer pessoa manda
  **qualquer mensagem para qualquer número** usando o WhatsApp da marca (que está no Vault, dentro da
  função — a pessoa não precisa da credencial, só da função). Isso é phishing com o número oficial do
  negócio, e a função ainda **engole erros de propósito** (`exception when others then null`), então
  o abuso não deixa rastro de erro. Alvo de alto valor.
- **`confirmar_pagamento_taxa` / `confirmar_pagamento_atendimento`** — combinadas com A2, `PUBLIC`
  aqui é bypass total de pagamento.

### Funções que eu considero de baixo risco (com o motivo)

| Função | Por quê |
|---|---|
| `is_admin()` | `coalesce(..., false)` fecha o NULL. Segura por construção |
| `current_usuario_id()` | é a origem do NULL, não a vítima |
| `piso_percentual()` | pura, sem permissão envolvida |
| `registrar_denuncia()` | checa `is_admin()` (que é seguro) antes de tudo |
| `expirar_reservas_vencidas()` | sem parâmetro de usuária; só o cron chama; pior caso é recusar reserva vencida |
| `periodos_ocupados()` | leitura pública por design, sem dado sensível |

### Ainda a inspecionar (não dá pra classificar sem o corpo)

- **`trg_reservas_before_insert()`** — a trava anti-autofraude compara o WhatsApp da compradora com o
  da vendedora. Se for `if compradora.whatsapp = vendedora.whatsapp then raise`, a direção é segura
  (falha aberta só se o WhatsApp for NULL). Mas ver **B6**: a trava é burlável por formatação mesmo
  estando "correta".
- **`trg_reservas_after_update()`** — ver **B3**: a preocupação aqui não é NULL, é falta de máquina de
  estados.
- **`handle_new_auth_user()`** — o cadastro manda `papel` no metadata do `signUp` (código:
  `src/app/cadastro/actions.ts`). O front restringe a `vendedora|loja|compradora|parceira`, mas o
  `signUp` é chamável direto pela API do Supabase com **qualquer** metadata. Se a lista branca dentro
  da função não excluir explicitamente `admin` e `embaixadora`, dá pra **se cadastrar como admin**.
  O snapshot diz que existe validação ("papel default 'compradora' se não vier um válido"), mas *qual*
  é a lista válida não está registrado. Precisa do corpo (Q2).
- **A função de cashback por clique que não está no snapshot** — ver B1.

## 2. Índices

Fato de base: **o Postgres não cria índice automaticamente em coluna de chave estrangeira.** Ele cria
só em chave primária e em restrição `UNIQUE`. Então, salvo os dois índices de `compartilhamentos`
citados no snapshot, a premissa realista é que **quase nenhuma FK deste banco tem índice**.

Há um agravante específico de Supabase: as políticas de RLS são subconsultas que rodam **por linha
avaliada**. Uma policy como `usuarios_select_apos_contato_liberado` (que existe transação paga ligando
as duas partes) percorre `transacoes → reservas → pecas` toda vez que alguém lê `usuarios` —
inclusive nos `select("*, usuarios(nome, whatsapp)")` espalhados pelo painel. Sem índice, isso vira
varredura completa de tabela multiplicada pelo número de linhas. É o tipo de coisa que funciona bem
com 200 peças e derruba o site com 20.000.

### Prioridade 1 — impacto imediato

| Índice sugerido | Por que |
|---|---|
| `usuarios(auth_user_id)` **UNIQUE** | **O caminho mais quente do sistema inteiro.** `current_usuario_id()`, `is_admin()`, `getCurrentUsuario()` e 4 policies de RLS fazem `where auth_user_id = auth.uid()`. Roda várias vezes por requisição, em toda página. Se estiver faltando, é a primeira coisa a criar. UNIQUE também vale semanticamente: uma conta de auth = uma usuária |
| `reservas(peca_id)` | FK. Usada por `periodos_ocupados`, `trg_reservas_before_insert`, RLS de `reservas`/`transacoes`/`usuarios` |
| `reservas(compradora_id)` | FK. `/painel/compradora` filtra por ela; RLS também |
| `transacoes(reserva_id)` **UNIQUE** | FK. Está no meio da policy `usuarios_select_apos_contato_liberado` (a mais cara do banco). UNIQUE resolve também o B3 — ver seção 3 |
| `pecas(dono_id)` | FK. `/painel/vendedora`, RLS de `pecas` e o join `reservas → pecas!inner(dono_id)` |
| `notificacoes(usuario_id, criado_em desc)` | O sino do menu roda `select * from notificacoes order by criado_em desc limit 20` **em toda página** para usuária logada, sem `where` — o filtro vem só da RLS. Índice composto nessa ordem permite pegar as 20 direto, sem ordenar a tabela toda |

### Prioridade 2 — crescem rápido com o uso

| Índice sugerido | Por que |
|---|---|
| `comissoes(parceira_id)` | FK. `/painel/parceira` + RLS |
| `comissoes(transacao_id)` | FK. Usada pelo `confirmar_pagamento_taxa` e por qualquer conferência de estorno |
| `comissoes(criado_em) where paga = false` (parcial) | painel admin lista só as pendentes |
| `avaliacoes(avaliado_id) where tipo_alvo in ('vendedora','locadora')` | a média da vendedora é calculada em **toda visita a `/pecas/[id]`** — página pública, a mais acessada do site |
| `avaliacoes(avaliador_id)` | FK. `/painel/compradora` verifica o que já foi avaliado |
| `avaliacoes(transacao_id)` | FK + necessária para a RLS de INSERT |
| `cashback(usuario_id) where usado = false` (parcial) | saldo é calculado em 3 telas diferentes |
| `favoritos(usuario_id, peca_id)` **UNIQUE** | o toggle faz "busca e depois insere" — sem UNIQUE, dois cliques rápidos criam duplicata. Também serve à vitrine |
| `cliques_compartilhamento(compartilhamento_id)` | FK + é o que a contagem de cliques usa |
| `cliques_compartilhamento(ip_hash, criado_em desc)` | é exatamente o `where` do throttle anti-fraude de 24h |
| `pecas(status, criado_em desc)` ou parcial `where status = 'aprovado'` | a vitrine pública inteira |
| `usuarios(recrutado_por)` | FK. Rede da embaixadora + cálculo de override em toda venda paga |
| `atendimentos_assistidos(usuario_id)` | FK + painel |
| `denuncias_banimento(vendedora_id)` | FK + painel admin |
| `reservas(prazo_confirmacao) where status = 'aguardando_confirmacao'` | o `pg_cron` roda a cada 15 min, pra sempre. Índice parcial mantém isso barato eternamente |

### Prioridade 3 — baixo volume, mas corretos

`reservas(compartilhamento_id)`, `transacoes(estornado_por)`, `usuarios(whatsapp)` (ver B6),
`transacoes(mp_payment_id)` UNIQUE e `atendimentos_assistidos(mp_payment_id)` UNIQUE — esses dois
últimos protegem contra o mesmo pagamento do Mercado Pago ser amarrado a duas cobranças.

### Observação prática sobre como criar

Com o volume atual (marketplace novo), `CREATE INDEX` comum leva milissegundos e o lock é
imperceptível. **Não** usar `CREATE INDEX CONCURRENTLY` agora: ele não roda dentro de transação, e o
`apply_migration` do MCP envolve tudo em transação — ia falhar. Quando as tabelas passarem de ~100k
linhas, aí sim vale o CONCURRENTLY via `execute_sql` avulso.

**Antes de criar qualquer coisa, rode Q4, Q5 e Q8** — Q8 (`pg_stat_user_tables`) mostra quais tabelas
o Postgres está de fato varrendo em produção, e isso reordena a lista acima com dado real em vez de
teoria.

## 3. Constraints de integridade — com custo/benefício

Critério que usei: **vale virar CHECK quando o dado é gravável pela API REST sem passar pelo código
da aplicação** (que é o caso de praticamente tudo aqui, já que o Supabase expõe as tabelas
diretamente) **e quando um valor inválido causa dano de negócio, não só feiura**.

### Faça agora (benefício alto, custo perto de zero)

| Constraint | Por quê | Risco de aplicar |
|---|---|---|
| `avaliacoes CHECK (nota between 1 and 5)` | Hoje a validação 1–5 existe **só no formulário React**. A RLS de INSERT libera qualquer nota pra quem tem uma transação paga. `nota = -999` entra e envenena a média pública da vendedora | Nenhum, se Q9 mostrar 0 linhas fora da faixa |
| `avaliacoes UNIQUE (transacao_id, tipo_alvo, avaliador_id)` | A tela esconde o formulário quando já avaliou, mas **nada no banco impede repetir o insert**. Com uma única compra paga, dá pra inserir 500 notas 1 e destruir a reputação de uma vendedora. Avaliação é leitura pública (`qual: true`), então o estrago aparece na vitrine | Nenhum, se Q9 não achar duplicata |
| `transacoes UNIQUE (reserva_id)` | Uma reserva = uma transação. Sem isso, o trigger de `confirmada` pode gerar N transações pra mesma reserva (ver B3) | Nenhum, se Q9 não achar duplicata |
| `favoritos UNIQUE (usuario_id, peca_id)` | Elimina a corrida do toggle e serve de índice | Nenhum |
| `reservas CHECK (status in ('aguardando_confirmacao','confirmada','recusada','contato_liberado'))` | A RLS deixa a **dona da peça** dar UPDATE em `reservas` sem restringir o valor de `status`. Ou seja, ela pode gravar `'contato_liberado'` (ou `'banana'`) sem pagamento nenhum. O CHECK não resolve a máquina de estados, mas fecha a metade grosseira do problema | Nenhum, se Q9 confirmar que só existem esses 4 valores |
| `transacoes CHECK (status_pagamento in ('pendente','pago','estornado'))` | mesma lógica; protege o que o admin e o webhook gravam | idem |
| `transacoes CHECK (valor_base >= 0 and valor_taxa >= 0 and cashback_utilizado >= 0 and percentual_taxa between 0 and 100)` | são as colunas de dinheiro do negócio. Valor negativo aqui = comissão negativa, cashback negativo, relatório errado | idem |
| `reservas CHECK (locacao_fim >= locacao_inicio)` | hoje isso é validado **só** em `src/app/pecas/[id]/actions.ts`. Um insert direto na API grava período invertido, que quebra o `periodos_ocupados` silenciosamente | idem |

### Faça, mas com consciência do atrito

| Constraint | Benefício | Custo real |
|---|---|---|
| `usuarios CHECK (papel <@ array['compradora','vendedora','loja','parceira','embaixadora','admin'])` | `papel` decide **taxa (20% vs 30%) e poder de admin**. Um valor com typo (`'Loja'`, `'lojas'`) não bate no `any(papel)` e a pessoa cai silenciosamente na taxa de 30% — erro caro e invisível | Cada papel novo exige um `ALTER TABLE` (segundos, com `NOT VALID` + `VALIDATE` se um dia a tabela crescer). Eu **recomendo fazer**: neste projeto o papel é dinheiro |
| `pecas CHECK (status in (...))` e `CHECK (preco_anunciado > 0)` | evita peça com preço 0 ou negativo entrando no cálculo de piso e de taxa | mesmo atrito de lista fechada |
| `cashback CHECK (valor > 0 and valido_ate > criado_em)` | cashback com validade no passado nasce morto e some do saldo sem explicação | baixo |
| `EXCLUDE` de sobreposição de datas de aluguel — `EXCLUDE USING gist (peca_id WITH =, daterange(locacao_inicio, locacao_fim, '[]') WITH &&) WHERE (status in ('aguardando_confirmacao','confirmada','contato_liberado'))` | Hoje a checagem de conflito é "consulta `periodos_ocupados`, depois insere" — duas pessoas reservando as mesmas datas ao mesmo tempo passam as duas. O `EXCLUDE` torna isso **impossível no banco** | Exige a extensão `btree_gist` e um teste com cuidado (é a constraint mais complexa da lista). Recomendo, mas como um passo separado, depois das outras |

### Eu **não** faria

| Ideia | Por que não |
|---|---|
| `CHECK` de formato no `whatsapp` (regex) | Formato de telefone brasileiro varia demais (com/sem 9, com/sem DDI, com máscara). Um regex apertado quebra cadastro em produção. **A solução certa aqui é normalizar, não restringir** — ver B6 |
| `CHECK (valor_taxa = valor_base * percentual_taxa / 100)` | Parece elegante, mas arredondamento e o abatimento por cashback tornam isso frágil: uma diferença de um centavo derruba a transação inteira em produção. Melhor deixar como *relatório de conferência* (uma query periódica), não como constraint |
| `CHECK` em `cidade`, `cor`, `tecido`, `tamanho` | Campos de catálogo que a Juliana vai querer mexer sem chamar dev. Lista fechada aqui gera fricção sem ganho de segurança |
| Trocar `text` por `enum` do Postgres nos status | Parece "mais correto", mas `ALTER TYPE ... ADD VALUE` tem restrições chatas (não roda dentro de transação em versões antigas) e vira dor de cabeça no fluxo via MCP. `text` + `CHECK` dá 95% do benefício com 10% do atrito |

### Além de constraints: dois buracos de integridade de negócio

**B5 — o estorno não desfaz o que o pagamento fez.** `estornarTransacao`
(`src/app/painel/admin/estorno-actions.ts`) marca `status_pagamento = 'estornado'` e devolve o
dinheiro no Mercado Pago. Mas `confirmar_pagamento_taxa` tinha criado três coisas: cashback de 10%
pra vendedora, comissão direta de 10% e override de 5%. **Nenhuma delas é revertida.** Resultado: a
compradora recebeu o dinheiro de volta, e a plataforma continua devendo comissão sobre uma venda que
não existe mais. O código até avisa "reverta o cashback manualmente", mas só no caso de pagamento
100% por cashback — o caso comum passa despercebido. Q9 quantifica quantas comissões hoje apontam
para transações não-pagas.

**C4 — `cashback` não guarda de qual transação veio.** As colunas são `usuario_id, origem, valor,
criado_em, valido_ate, usado`. Sem um `transacao_id`, é **impossível** automatizar a reversão acima, e
também impossível auditar "esse cashback veio de qual venda?". Recomendo adicionar
`transacao_id uuid null references transacoes(id)` (nulo para os créditos de compartilhamento).
Relacionado: `usado boolean` não registra *onde* foi usado nem permite uso parcial — se um crédito de
R$15 abater uma taxa de R$10, precisa ficar claro se os R$5 restantes são perdidos (e se isso é a
intenção da Juliana). Q9 tem uma query que mostra se isso já aconteceu.

**B6 — o `whatsapp` é chave de negócio sem ser chave de banco.** Duas consequências reais:
1. A trava anti-autofraude do `trg_reservas_before_insert` compara os WhatsApps de compradora e
   vendedora. Como o número é gravado exatamente como digitado, `(11) 99999-9999` e `11999999999`
   são strings diferentes → **a mesma pessoa compra da própria peça** e a trava não vê nada. Isso
   fura direto a regra do blueprint ("trava de mesmo WhatsApp entre comprador/vendedor").
2. `promoverPapel` e `definirRecrutadoPor` no painel admin buscam por `whatsapp` com `maybeSingle()`.
   Se existirem dois cadastros com o mesmo número em formatos diferentes, a admin não acha ninguém;
   se existirem dois idênticos, o `maybeSingle()` **dá erro**.
   **Recomendação:** normalizar (guardar só dígitos, com DDI) e criar
   `UNIQUE INDEX on usuarios ((regexp_replace(whatsapp,'\D','','g')))`. A normalização mexe em dado
   existente, então precisa de Q10 antes (quantos números estão em formatos diferentes hoje).

**B1 — a anti-fraude do cashback por clique tem o mesmo problema de NULL.** A policy é
`INSERT cliques_insert_publico with_check: true` — qualquer um, inclusive `anon`. Isso é necessário
para a rota `/r/[id]` funcionar sem login, mas significa que **dá pra inserir cliques direto na API
REST do Supabase, sem passar pela rota**, e nesse caso `ip_hash` fica `NULL`. Qualquer throttle escrito
como `where ip_hash = <hash> and criado_em > now() - interval '24 hours'` **nunca casa com linhas de
`ip_hash` NULL** — então a defesa some exatamente para o atacante que a está atacando, enquanto
continua valendo para a usuária honesta que vem pela rota. O teto de 3 créditos/dia por usuária (se
existir mesmo) é o que segura o prejuízo em R$45/dia por conta. Precisa do corpo do trigger (Q3) e,
provavelmente, de duas correções: contar clique com `ip_hash IS NULL` como suspeito (ou recusá-lo) e
tirar o `INSERT` de `anon` em favor de uma função `SECURITY DEFINER` que só a rota chame.

## 4. Gap de migrations — como sair disso sem quebrar o fluxo atual

### O diagnóstico honesto

O schema de produção **só existe em produção**. Não há `supabase/migrations/`, não há `.sql` nenhum no
repositório (confirmei: zero arquivos), e `src/types/database.ts` é mantido à mão e já se sabe
dessincronizado. Isso significa, na prática:

- Ninguém consegue revisar uma mudança de banco antes dela existir (não há diff, não há PR).
- Não existe rollback documentado — só "lembrar o que estava antes".
- Não dá pra recriar o banco em outro lugar (staging, ambiente de teste, ou **recuperação de
  desastre**). Hoje, se o projeto Supabase for perdido ou corrompido, o schema se perde junto.
- E — o mais relevante pra esta auditoria — **é por isso que auditar custa tanto**: eu precisei de um
  snapshot manual, e o snapshot está incompleto.

Ao mesmo tempo, o fluxo "aplicar direto via MCP" é rápido e o time gosta dele. **A recomendação não é
trocar de fluxo, é adicionar o versionamento por cima dele.**

### O plano em 5 passos (ordem importa)

**Passo 1 — baseline (1 hora, zero risco).** Criar `supabase/migrations/20260816000000_baseline.sql`
com o schema atual completo. Duas formas:

```bash
# preferida — não altera nada em produção, só lê:
npx supabase db dump --db-url "postgresql://postgres:<senha>@db.izichohddofqylifppwh.supabase.co:5432/postgres" \
  --schema public -f supabase/migrations/20260816000000_baseline.sql
```

Se isso exigir Docker (dependendo da versão do CLI), o plano B é gerar o baseline **pelo próprio MCP**,
com as queries Q1–Q7 desta auditoria: elas devolvem tabelas, colunas, defaults, constraints, índices,
policies e o `pg_get_functiondef` de cada função — que é literalmente o conteúdo de um dump. Menos
elegante, mesmo resultado.

**Passo 2 — regra de ouro daqui pra frente (custo: 5 minutos por mudança).**
Toda DDL aplicada via MCP tem que virar um arquivo no repo **na mesma sessão**, com o SQL exato que
foi aplicado. Não é burocracia: é o arquivo que permite revisão, rollback e recriação. Template:

```sql
-- supabase/migrations/20260817143000_indices_fk.sql
-- Autor: @data-engineer (Dara)  |  Aplicado em produção via MCP: SIM (2026-08-17 14:30 BRT)
-- Motivo: FKs sem índice (auditoria docs/auditoria/dados-2026-08-16.md, item B4)
-- Impacto: nenhum bloqueio esperado (tabelas < 10k linhas)

create index if not exists idx_reservas_peca_id on public.reservas (peca_id);

-- ROLLBACK
-- drop index if exists public.idx_reservas_peca_id;
```

**Passo 3 — template obrigatório para funções (isso é o que evita o próximo incidente).**
Toda migration que contenha `CREATE OR REPLACE FUNCTION` **tem que terminar com o bloco de grants**,
porque o `CREATE OR REPLACE` reseta tudo para `PUBLIC`:

```sql
create or replace function public.minha_funcao(...) ... $$;

-- OBRIGATÓRIO: CREATE OR REPLACE reseta as grants para PUBLIC
revoke execute on function public.minha_funcao(...) from public;
revoke execute on function public.minha_funcao(...) from anon;
grant  execute on function public.minha_funcao(...) to authenticated;  -- ou nenhum grant, se for service_role
```

Sugiro guardar isso como `supabase/migrations/_TEMPLATE_function.sql` no repo, para virar copy-paste.

**Passo 4 — matar a dessincronização dos tipos (30 minutos, ganho permanente).**

```bash
npx supabase gen types typescript --project-id izichohddofqylifppwh > src/types/database.ts
```

Isso não precisa de Docker, só de `SUPABASE_ACCESS_TOKEN`. Colocar como script no `package.json`
(`"db:types"`). E o bônus: rodar isso e checar se o arquivo mudou é um **detector de drift grátis** —
se o comando altera `database.ts`, alguém mexeu no banco sem versionar:

```bash
npm run db:types && git diff --exit-code src/types/database.ts   # falha = banco divergiu do repo
```

Vale rodar semanalmente, ou como step de CI antes de deploy.

**Passo 5 — quando/se o CLI for adotado de vez.** O comando que faz o CLI conviver com o fluxo MCP é
`supabase migration repair --status applied <versão>`: ele marca uma migration como já aplicada sem
executá-la. Ou seja, o time continua aplicando pelo MCP e só "registra" no CLI depois — sem risco de
re-executar DDL em produção.

### O que eu **não** recomendo agora

- **Não** migrar para "só via CLI, nunca mais MCP". O ganho não compensa a perda de velocidade num
  time pequeno, e a disciplina do Passo 2 já entrega 80% do valor.
- **Não** criar tabelas de backup dentro do próprio Supabase antes de mudanças. Para este banco, o
  caminho é `pg_dump` (ou o backup automático do Supabase, que precisa ser **verificado** — vale
  confirmar no painel se está ativo e qual a retenção do plano atual).
- **Staging:** o ideal seria um segundo projeto Supabase (gratuito) restaurado a partir do baseline do
  Passo 1. Só faz sentido **depois** do Passo 1 — sem baseline, não há o que restaurar. Enquanto isso
  não existir, o padrão de teste seguro em produção continua sendo
  `begin; ... ; rollback;` (que foi exatamente o que provou o bug de 16/08).

## 5. Bucket `pecas-fotos`

### O que está lá hoje

Bucket único, **público**, sem `file_size_limit`, sem `allowed_mime_types`. INSERT liberado para
qualquer usuária autenticada (`auth.role() = 'authenticated'`), sem restrição de pasta.

### Avaliação — sim, merece correção, mas não é urgência de segurança

Não é o mesmo tipo de bug dos pagamentos: **exige estar logada**, e qualquer pessoa pode criar uma
conta em 30 segundos. O risco não é vazamento de dado; é **abuso de recurso e de reputação**:

1. **Custo:** storage e egress do Supabase são cobrados. Sem limite de tamanho, uma conta pode subir
   arquivos de gigabytes. A conta é da Juliana.
2. **Hospedagem parasita:** o bucket é público e o domínio é do Supabase — vira hospedagem gratuita
   de qualquer arquivo (inclusive conteúdo ilegal), associada ao projeto do negócio.
3. **Tipos perigosos:** sem lista de mime, dá pra subir `.html` ou `.svg` e ter uma URL pública
   servida pelo domínio do projeto — útil para phishing. (Impacto direto no site é limitado, porque o
   domínio do Supabase é uma origem diferente da do app.)

### Recomendação — em duas etapas, nessa ordem

**Etapa 1 (segura, faça): limite de tamanho + lista de mime types.**
Antes de aplicar, rode **Q11**, que mostra quais tipos e tamanhos já existem no bucket. Isso é
essencial por um motivo bem prático: **iPhone envia HEIC**. Se a lista branca não incluir
`image/heic`/`image/heif`, o upload quebra em produção para uma boa parte das vendedoras — e o
formulário (`nova-peca-form.tsx`) sobe o arquivo original **do jeito que veio**, só a versão com marca
d'água é convertida para JPEG. Sugestão de partida, a ajustar conforme Q11:
`image/jpeg, image/png, image/webp, image/heic, image/heif, video/mp4, video/quicktime`
(o `.mov` do iPhone é `video/quicktime`), com `file_size_limit` de ~50 MB — o mesmo bucket recebe
vídeo, então um limite de 10 MB quebraria o upload de vídeo.

**Etapa 2 (faça depois, com teste): restringir upload à pasta da própria usuária.**
Boa notícia: o código já organiza tudo por pasta de usuária —
`` `${user.id}/${id}-original.jpg` `` em `nova-peca-form.tsx` e em `editar-peca-form.tsx`. Então a
policy abaixo é compatível com o app como está hoje:

```sql
-- with_check da policy de INSERT (substitui a atual)
bucket_id = 'pecas-fotos' and (storage.foldername(name))[1] = auth.uid()::text
```

O único ponto a verificar antes é `foto-editorial-actions.ts`, que também faz upload — precisa
confirmar que ele usa o mesmo formato de path (e ele roda com service role, que ignora RLS de
qualquer forma). Como uma policy errada **quebra o cadastro de peça em produção**, essa etapa merece
ser aplicada e testada com um upload real logo em seguida.

**Não recomendo agora:** tornar o bucket privado com URLs assinadas. A vitrine é pública por design,
e isso adicionaria complexidade (e latência) sem ganho real.

## 6. Regra de negócio: embaixadora paga 30%, não 20%

**A leitura está correta e o comportamento é intencional.** O README é ambíguo, mas o blueprint é
explícito — e ele é a fonte de verdade do produto:

> **Embaixadora de cidade:** parceira com território... Tem loja própria dentro da plataforma, mas
> **paga a taxa padrão (30%) sobre os produtos dela — não o desconto de loja.**
> — `blueprint-e-meu-pode-ser-seu.md`, seção de papéis

E na seção de regras: *"A embaixadora tem sua própria loja na plataforma, mas paga a taxa padrão de
pessoa física/loja normal sobre os produtos dela — não tem desconto por ser embaixadora."*

Ou seja, a ordem do `CASE` (`'embaixadora' = any(papel)` **antes** de `'loja' = any(papel)`) é o
comportamento desejado, não um acidente de escrita. Faz sentido econômico: a embaixadora já ganha
comissão direta (10%) e override (5%); dar também o desconto de loja empilharia três benefícios sobre
a mesma pessoa.

**O que eu sinalizaria pra Juliana (não é bug, é decisão não documentada):**

| Caso | O que acontece hoje | Está no blueprint? |
|---|---|---|
| Loja **e** embaixadora | paga **30%** | Sim, explícito |
| Loja **e** parceira (não embaixadora) | paga **20%** (mantém o desconto) | **Não** — o blueprint só fala da embaixadora |
| Loja com **venda assistida** | paga **60%** (venda assistida ganha de tudo) | Implícito, mas nunca dito com todas as letras |

Os dois últimos são interpretações razoáveis do código, mas ninguém confirmou. Vale uma pergunta
direta de uma frase pra Juliana: *"uma loja que também é parceira continua pagando 20%, certo? E se
ela pedir venda assistida, sobe pra 60% mesmo sendo loja?"*

**Sugestão de custo zero e valor alto:** gravar essa decisão como `COMMENT ON FUNCTION` no próprio
banco, para que a regra fique junto do código que a implementa e ninguém "conserte" a ordem do `CASE`
achando que é bug:

```sql
comment on function public.trg_reservas_after_update() is
  'Ordem do CASE é INTENCIONAL: embaixadora é avaliada ANTES de loja, então quem tem os dois papéis
   paga 30% (padrão), não 20%. Fonte: blueprint-e-meu-pode-ser-seu.md, seção de papéis.';
```

Detalhe adicional (comportamento correto, só para registro): o percentual é decidido **no momento da
confirmação da reserva** e congelado em `transacoes.percentual_taxa`. Se a admin promover a vendedora
a embaixadora depois disso, a transação antiga não muda — o que é o comportamento certo e auditável.

### Q5 — chaves estrangeiras: quais estão sem índice e o que acontece no DELETE `[destrava B4]`

```sql
select
  c.conrelid::regclass::text as tabela,
  c.conname                  as constraint_name,
  (select string_agg(a.attname, ',' order by k.ord)
     from unnest(c.conkey) with ordinality k(attnum, ord)
     join pg_attribute a on a.attrelid = c.conrelid and a.attnum = k.attnum) as colunas_fk,
  c.confrelid::regclass::text as referencia,
  case c.confdeltype when 'a' then 'NO ACTION' when 'r' then 'RESTRICT'
       when 'c' then 'CASCADE' when 'n' then 'SET NULL'
       when 'd' then 'SET DEFAULT' end as on_delete,
  exists (select 1 from pg_index i
          where i.indrelid = c.conrelid and i.indkey[0] = c.conkey[1]) as tem_indice_na_coluna
from pg_constraint c
where c.contype = 'f' and c.connamespace = 'public'::regnamespace
order by tem_indice_na_coluna, 1, 2;
```

(O `on_delete` importa: se `transacoes`/`comissoes` estiverem como `CASCADE` a partir de `usuarios`,
apagar uma usuária apaga registro financeiro — o correto para dado financeiro é `RESTRICT`.)

```sql
from usuarios
group by 1 having count(*) > 1
order by 2 desc;
```

(Se a segunda query devolver alguma linha, existe hoje mais de um cadastro para o mesmo número — e a
trava anti-autofraude já pode ter sido furada, de propósito ou não.)

### Q11 — configuração e conteúdo real do bucket `[destrava C3]`

```sql
select id, public, file_size_limit, allowed_mime_types, created_at from storage.buckets;

select metadata->>'mimetype' as mime,
       count(*) as arquivos,
       pg_size_pretty(max((metadata->>'size')::bigint)) as maior_arquivo,
       pg_size_pretty(sum((metadata->>'size')::bigint)) as total
from storage.objects
where bucket_id = 'pecas-fotos'
group by 1
order by 2 desc;

-- confere se todo objeto está mesmo dentro de uma pasta com uuid de usuária
select count(*) filter (where (storage.foldername(name))[1] ~ '^[0-9a-f-]{36}$') as no_padrao_uuid,
       count(*) filter (where (storage.foldername(name))[1] !~ '^[0-9a-f-]{36}$') as fora_do_padrao,
       count(*) as total
from storage.objects where bucket_id = 'pecas-fotos';
```

### Q13 — privilégios de tabela de `anon` e `authenticated` (RLS só vale se o GRANT existir)
